# 概要

担当者名（username）の空き確認。regist.html が Cognito の `signUp` を呼ぶ**前**に叩く。

# インターフェース仕様

登録フローは以下の順序になる。

- ①フロントがこのAPIで担当者名の空きを確認する
- ②空いていれば Cognito の `signUp` → 確認コード入力で `confirmRegistration`
  - **`signUp` の `Username` に渡すのはメールアドレス**で、担当者名ではない
    （Cognito のサインイン設定が「Email のみ」のため。[index.md](../IF/index.md#ログインidはメールアドレス)）
  - つまり担当者名の一意性は Cognito では担保されない。**このAPIと `POST /user` だけが
    担当者名の重複を見ている**
- ③確認が通った後に `POST /user`（regist.md）を呼び、UsersTable にユーザーを登録する

①を挟むのは、Cognito側にユーザーを作ってしまってから `POST /user` の重複チェックで
弾かれると、Cognitoには確認済みユーザーが存在するのにUsersTableには登録できない
「孤児アカウント」が発生するため。事前にここで弾くことでその発生を抑える。

なお、このチェックとCognitoの`signUp`呼び出しの間には短いレースコンディションが
残る（同時に同じ担当者名で登録した場合など）。その場合の最終的な重複防止は
引き続き `POST /user`（regist.md）側の `ConditionExpression` が担う。

## API パス

- `/user/check`

## メソッド

- `GET`

## リクエスト

### クエリパラメータ

| パラメータ | 必須 | 内容                                   |
| ---------- | ---- | -------------------------------------- |
| username   | Yes  | 確認したい担当者名（3-20文字の日本語） |

文字数・文字種の規則は `POST /user`（[regist.md](../IF/regist.md)）と**同一**にすること。
片方だけ厳しいと、フロントの入力検証を通った担当者名が登録の途中で弾かれ、どちらの
API で止まったのか分からない状態になる（2026-10-05 に 6文字以上／4文字以上／3文字以上が
3箇所で食い違っていた問題を、3文字以上に統一して解消した）。

### リクエストボディ

なし

## レスポンス

### ステータスコード

- `200 OK`: 正常なレスポンス（`exists` で空き状況を返す）
- `400 Bad Request`: パラメータエラー（未入力・文字種/文字数違反）
- `500 Internal Server Error`: サーバーエラー

### レスポンスボディ

```json
{
  "msg": "",
  "exists": false // true: 既に使用されている / false: 空いている
}
```
