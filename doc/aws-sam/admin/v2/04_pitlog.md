## 1. 位置づけ

3つの画面は、**同じデータ・同じ形式・同じ描画処理**を使う。違うのは次の3点だけ。

| 画面                    | 見られる race                                  | 出力（ダウンロード） | ログに残すか |
| ----------------------- | ---------------------------------------------- | -------------------- | ------------ |
| `showAll.html`（確認）  | 入室中の1レースのみ（終了すると見られない）    | できない             | **残さない** |
| `outPosts.html`（出力） | 入室中の1レースのみ（終了すると見られない）    | できる               | 残す         |
| 管理者ポップアップ      | **所属サーキットの全レース**（終了済みも含む） | できる               | 残す         |

- **見られる race の違いは、画面が持っている `raceId` の数で決まる。** 一般画面は conform で入室したときの `raceId` を sessionStorage に1つ持つだけなので、そのレースしか見られない。管理者ポップアップは一覧から選ぶため、自分のサーキットのレースならどれでも開ける。
- **終了済みを見られるかは、画面ではなく人（leader かどうか）で決まる。** 01章 §5.1 と §5.4 の違いがそのまま出る。そのため、leader が一般画面を開いた場合は、終了済みのレースでも 403 にならない（見られるのは入室中の1レースのみという点は変わらない）。
- `raceId` はヘッダー（`X-Race-Id`）で送る（01章 R10）。

## 2. バックエンドのデータ処理

### 2.1 現状の問題（`showAll.mjs`）

今は1本の Lambda が、データ取得・加工・認可・記録を全部やっている。直すべき点は3つ。

| #   | 現状                                                                                          | 直す内容                   |
| --- | --------------------------------------------------------------------------------------------- | -------------------------- |
| 1   | 認可が `username` の有無だけ。race の存在確認も終了判定もサーキット照合も無い                 | §3.3 の認可を通す          |
| 2   | レスポンスが ULID をキーにしたオブジェクト。フロントは結局 `Object.keys()` で配列に戻している | 最初から配列で返す（§3.1） |
| 3   | 仮キーを書いてすぐ消す無意味なコードが残っている（`result[...] = null` → あとで `delete`）    | 削除する                   |

### 2.2 共通化: `buildPitLogs(raceId)`

データを組み立てる部分を、Layer（`/opt/nodejs/`）の共通関数に切り出す。認可も記録も**含めない**（呼び出し側の責任にする）。

> **現行の `showAll.mjs` から手順の順序を変える。** 前回のデバッグで、並び順が「車番 → ピット回数」のままで**ピット時間順になっていない**ことが判明した。かつ、時間順に並べ替えてからドライバーを計算すると引き継ぎが壊れるため、**「車ごとに計算 → 最後に時間順へ並べ替え」** の順序にする必要がある。

やること:

1. `pit_log` / `entry` / `retire` / `start_driver` を `race_id` で並列に Query する
   - `entry` / `start_driver` / `retire` は、車番から引けるよう「車番 → 行」の対応表にしておく
2. **車ごとに分け、各車の中をピット回数の昇順に並べる**（この並びは計算のためのもので、最終的な表示順ではない）
3. **車ごとにドライバーを決める（§2.3 のキュー方式）**
   - 算出した `inDriver` / `outDriver`（`A`〜`F`）から `entry.driver_a`〜`driver_f` を引いて**氏名**も付ける（`inDriverName` / `outDriverName`）。枠が null、または記号自体が null のときは氏名も `null`
4. `pitGap` を算出する（`inTime` / `outTime` が**両方揃っているときだけ**、その差を秒数で。片方でも欠けていれば `null`）
5. `entry` から `className` / `teamName` / `maintenanceArea` / `pitGarage`、`retire` から `retire` を引いて合成する
6. **全車をまとめ、`inTime` → `carNum` の昇順に並べ替える**（§2.4）
7. **配列**で返す

### 2.3 ドライバーの決め方（キュー方式）

1台ぶんの記録を、**スタートドライバーを先頭に置いた1本の列**として扱う。

```
startDriver → pit_log 1回目の driver_out → pit_log 2回目の driver_out → …
```

この列の**隣り合う2つ**が、そのまま1回ぶんの「入った人／出た人」になる。

| 対象の記録 | inDriver（入った人） | outDriver（出た人） |
|---|---|---|
| 1回目 | `startDriver` | 1回目の `driver_out` |
| 2回目 | 1回目の `driver_out` | 2回目の `driver_out` |
| 3回目 | 2回目の `driver_out` | 3回目の `driver_out` |

**具体例**（5号車。スタートは枠A、各回の `driver_out` が B → C）

| pit_num | 列の位置 | inDriver | outDriver | 氏名（entry から引く） |
|---|---|---|---|---|
| 1 | `A` と `B` の間 | **A** | **B** | あそう太郎 → きたのせいじ |
| 2 | `B` と `C` の間 | **B** | **C** | きたのせいじ → さとうじろう |

- 「ピットに入ってきた人は、前回出ていった人」という引き継ぎになる。1回目だけは前が無いので `start_driver` を使う。
- **この計算は必ず車ごと・ピット回数順に行う。** 他の車の記録が間に挟まると引き継ぎが崩れるため、手順2で車ごとに分けている。
- `start_driver` が未登録の車は、1回目の `inDriver` が `null` になる。

### 2.4 並び順（最終的な表示順）

**「その記録の時刻」→ `carNum` の昇順**にする。レース中の動きを時系列で追えるようにするため。

```
その記録の時刻 ＝ inTime があればそれ、無ければ outTime
```

| 記録の種類 | inTime | outTime | 並びに使う時刻 |
|---|---|---|---|
| 通常のピットイン・アウト | 13:05 | 13:07 | **13:05** |
| まだピットから出ていない | 13:05 | null | **13:05** |
| ガレージスタート（出ただけ） | null | 13:00 | **13:00** |

- `inTime` だけで並べると、ガレージスタート（`inTime` が無い）が末尾に飛ばされ、**レース開始時の出来事が最後に表示されてしまう**。上の方式なら、実際に起きた時刻の位置に並ぶ。
- 逆に `outTime` を主軸にすると、**まだピットから出ていない車**（作業中でいちばん見たい記録）が末尾に飛ばされるため採らない。
- 時刻が同じときは、車番の小さい順にする（結果が毎回同じになるように）。
- 両方 `null` の記録は末尾に置く（登録時のバリデーションで弾いているため、通常は発生しない）。

> 現行実装は「車番 → ピット回数」の順で返しており、時系列になっていない。フロント側（`showAllGimic.js`）も `pitNum` を優先して並べ替えているため、**両方を直す必要がある**（§4.1・§7）。

### 2.5 `garageInTime`（ガレージイン時刻）は扱わない

**ガレージインは入力画面から廃止済み**（`htmls` のコミット `e1eac3d`「enterAuto: ガレージイン廃止しイン/アウトのみに簡素化」2026-06-22）。本章のレスポンスには含めない。

ただし、**廃止されたのは enterAuto の操作だけで、データ構造としては各所に残っている**。

| 層 | 残っている箇所 |
|---|---|
| フロント | `enterHand.js`（常に `garageInTime: null` を送る）、`showAll.js` / `outPosts.js`（受け取って保持） |
| バックエンド | `autoCreate.mjs` / `handCreate.mjs`（「inTime / outTime / garageInTime のいずれかは必須」のバリデーションと保存）、`showAll.mjs` / `updateGet.mjs`（`pitGap` の条件とレスポンス）、`updatePut.mjs`（変更項目として受付） |

これらの削除は、**実装のタイミングでまとめて行う**（§7）。本章ではレスポンスから外すところまでを決める。

## 3. 送信形式

### 3.1 レスポンス（3画面共通）

```json
{
  "msg": "",
  "logs": [
    {
      "pitNum": 1,
      "carNum": 5,
      "manager": "あそう太郎",
      "retire": false,
      "inDriver": "A",
      "inDriverName": "あそう太郎",
      "outDriver": "B",
      "outDriverName": "かんざきあおい",
      "inTime": "2026-08-30T13:05:00+09:00",
      "outTime": "2026-08-30T13:07:30+09:00",
      "pitGap": 150,
      "className": "ST-1",
      "teamName": "チームA",
      "maintenanceArea": 1,
      "pitGarage": "T1",
      "tire": true,
      "oil": false,
      "note": ""
    }
  ]
}
```

**項目の並びは、画面の列の並びに揃えてある**（見比べやすくするため）。ただし JSON のキーの順序は動作には影響しない（フロントは名前で取り出す）ので、実装側が守るべき決まりではない。

- 0件のときは `logs: []`。
- 並び順は **「その記録の時刻（`inTime` ?? `outTime`）」→ `carNum` の昇順**（§2.4）。画面側で並べ替え直せる。
- **`garageInTime` は含めない。** ガレージインは入力画面から廃止済み（§2.5）。

**`pit_log.id`（ULID）は返さない。** 理由は次のとおり。

- 記録の書き換え（`PUT /entries/update`）は `race_id` + `carNum` + `pitNum` で対象を特定しており、ULID を使っていない（[updatePut.mjs](../../../../backend-sam/functions/pitlog/updatePut.mjs) で確認済み）。
- 表示にも出力にも使っていない。現行の `showAllGimic.js` は同時刻の並べ替えに使っているが、ULID は文字列のため `a.managerId - b.managerId` が `NaN` になり、**実際には何もしていない**。
- 使わない内部キーを画面や通信に流さないほうが安全（`raceId` と同じ考え方。01章 §1）。

### 3.2 項目

画面の列の並び順に記載する。**太字**は今回追加した項目（現行の出力画面には無い）。

| #   | 項目              | 内容                                                                                           |
| --- | ----------------- | ---------------------------------------------------------------------------------------------- |
| 1   | `pitNum`          | **ピット回数**（何回目のピットインか。場所ではない。§8）                                      |
| 2   | `carNum`          | 車番                                                                                           |
| 3   | `manager`         | 記録した担当者                                                                                 |
| 4   | `retire`          | `retire` テーブルから引く                                                                      |
| 5   | `inDriver`        | 入ったときの運転者の**枠**（`A`〜`F`）。`pitNum=1` は `start_driver`、2以降は前回の `outDriver` |
| 6   | **`inDriverName`** | 上の枠に対応する**氏名**。`entry.driver_a`〜`driver_f` から引く。該当が無ければ `null`         |
| 7   | `outDriver`       | 出たときの運転者の**枠**（`A`〜`F`）                                                           |
| 8   | **`outDriverName`** | 上の枠に対応する**氏名**。該当が無ければ `null`                                               |

| 13  | `teamName`        | `entry` から引く                                                                               |

| 16  | **`tire`**        | タイヤ交換の有無                                                                               |
| 17  | **`oil`**         | 給油の有無                                                                                     |
| 18  | `note`            | 備考                                                                                           |

`garageInTime` は含めない（§2.5）。

### 3.3 エンドポイントと認可

**エンドポイントは1本にする。** 3画面とも同じものを呼び、Lambda が呼び出し元の権限を見て扱いを変える。

`GET /entries/show`（既存のパスを流用）

| クエリ  | 内容                                                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------- |
| `act=1` | 付けると `OutpostLog` に記録する（§6）。`outPosts.html` と管理者ポップアップが付ける。`showAll.html` は付けない |

処理の順序（**2026-10-09実装**。トークン移行後の形に更新）:

1. `authorizer.username` が無ければ **401**
2. **呼び出し元が leader か**で分岐する。**分岐はトークン検証より前に行う**（送られてくるものが違うため）
   - **leader の場合:** `X-Race-Id` は**平文の raceId**（管理者APIは raceId トークンの対象外。01章 R10・`raceToken.js` 冒頭）。`requireAdmin` で leader とサーキットを確認し、`requireRace`（`write` 指定なし）で race を取得する。**存在しない／他サーキットは 404、終了済みでも続行**（01章 §5.1）
   - **leader でない場合:** `X-Race-Id` は**署名付きトークン**。`requireGeneralRace` で検証する。終了済み（`exp` 超過）なら **403**（`reason: "race_finished"`）、その他の不正も **403**（01章 §5.4）
3. `buildPitLogs(raceId)` でデータを組み立てる
4. `act=1` なら `OutpostLog` に記録する（`is_leader` も残す）
5. 返す

- **レースタイトル（`raceTitle`）の取り方が分岐で違う。** leader は `requireRace` が返した race をそのまま使う（引き直さない）。一般利用者はトークンに raceId しか入っていないため、`RaceTable` を1回引く。
- 認可の部品は管理者APIと同じもの（`admin.js` の `requireAdmin`・`raceAccess.js` の `requireRace`）を流用する。IAM は既存の `RaceDataLambdaRole` で足りる（`UsersTable` の `GetItem` と `RaceTable` の `GetItem` を既に許可している）。

> **なぜ1本にするか:** 返すデータも形式も同じで、違うのは認可だけ。2本に分けると、ほぼ同じ中身の Lambda を2つ保守することになる。「終了済みを見られるかは、どの画面から呼んだかではなく、その人が leader かどうかで決まる」という考え方に揃える。

### 3.4 エラー

| 条件                           | コード | msg                                                 |
| ------------------------------ | ------ | --------------------------------------------------- |
| 未ログイン                     | 401    | 「認証が必要です」                                  |
| **leader で、race が存在しない／他サーキットの race** | 404    | 「対象のレースが存在しません」（どちらも同じ。存在を知られないため） |
| leader だが `users` に登録が無い | 403    | 「ユーザーが見つかりません」（`reason: "user_not_found"`。`requireAdmin`） |
| leader でなく、race が終了済み | 403    | 「終了したレースです」（`reason: "race_finished"`） |
| leader でなく、トークンが不正   | 403    | 「大会IDを確認できません。入室し直してください」（`reason` なし） |
| サーバーエラー                 | 500    | 「サーバーエラーが発生しました」                    |

**一般利用者には 404 が無い。** トークン方式では race を引かないため（01章 §5.4）。`404` は leader の経路（`requireRace`）だけで返る。

### 4.2 共通化の方針（2026-10-09実装済み）

`showAllGimic.js` から **DOM の決め打ちとグローバル変数を取り除き、引数で受け取る純粋な関数にした。**

| 関数                                                             | 役割                                       |
| ---------------------------------------------------------------- | ------------------------------------------ |
| `filterAndSortPitLogs(logs, { className, search })`              | 絞り込みと並べ替えをして、新しい配列を返す |
| `renderPitLogHead(thead)`                                        | 列定義から見出し行を作る（§4.3）           |
| `renderPitLogTable(tbody, logs)`                                 | 渡された `tbody` に行を描く                |
| `renderClassButtons(filterList, classNames, selected, onSelect)` | クラス絞り込みのボタンを作る（状態は持たない） |
| `formatDriver` / `formatDatetime` / `formatGap` / `formatBoolean` | 表示用の整形（従来のまま）                 |

- **イベントの紐付け（検索欄・クラスボタン・全表示ボタン）は、各画面の側に移した。** `showAll.js` / `outPosts.js` / 管理者画面が、自分の画面にある要素を自分で拾って、上の関数を呼ぶ。絞り込みの状態（`{ className, search }`）も各画面が持つ。
- **クラスボタンの生成だけは共通部品に残した。** 生成そのものは3画面で同じで、重複させる意味が無いため。ただし**状態は持たせず**、置き場所の要素・候補・選択中の値・押されたときに呼ぶ関数を引数で受け取る形にしてある（DOM の決め打ちもグローバル変数も無いため、§4.2 の目的は満たす）。
- `showAllGimic.js` の中に `document.getElementById` / `document.querySelector` は無く、`document.createElement` だけが残っている。
- これにより、`showAllGimic.js` は「どの画面から呼ばれても同じように動く部品」になった。
- 管理者ポップアップでも、一般画面と同じ絞り込み・並べ替えがそのまま使える。
- **読み込み順**: 部品を先に読むため、各HTMLの `<script>` は `common.js` → `showAllGimic.js` → 画面のJS の順にし、画面側の入口は `DOMContentLoaded` に揃えた（admin 系と同じ形）。

### 4.3 列の定義（表示とダウンロードの共通の正）

**画面に出す列の一覧を1箇所にまとめ、表の描画とダウンロードの両方がこれを使う。**

```js
const PIT_LOG_COLUMNS = [
  { key: "maintenanceArea", label: "作業エリア" },
  { key: "carNum",          label: "ゼッケン番号" },
  { key: "manager",         label: "担当者" },
  { key: "retire",          label: "リタイア",         format: formatBoolean },
  { label: "インドライバー",   value: (r) => formatDriver(r.inDriver,  r.inDriverName)  },
  { label: "アウトドライバー", value: (r) => formatDriver(r.outDriver, r.outDriverName) },
  { key: "inTime",          label: "ピットイン",       format: formatDatetime },
  { key: "outTime",         label: "ピットアウト",     format: formatDatetime },
  { key: "pitGap",          label: "ピットGAP",        format: formatGap },
  { key: "oil",             label: "給油",             format: formatBoolean },
  { key: "tire",            label: "タイヤ交換",       format: formatBoolean },
  { key: "className",       label: "クラス名" },
  { key: "teamName",        label: "チーム名" },
  { key: "note",            label: "備考" },
];
```

- 各列は、単純に1項目を出すなら `key`、複数の項目を組み合わせるなら `value(row)` を持つ。
- **見出し行は `renderPitLogHead(thead)`、データ行は `renderPitLogTable(tbody, logs)`** が、この配列を回して作る（HTMLに直書きしない）。列数も `PIT_LOG_COLUMNS.length` から取るため、`colSpan = 12` の決め打ちが消える。`showAll.html` / `outPosts.html` の `<thead>` は空にしてあり（`id="thead"`）、列を足しても見出しと本文がずれない。
- **CSV のダウンロードも、同じ配列を回して作る**（§5）。
- この結果、**画面に出ている列とダウンロードされる列が、常に一致する。** 列を足したいときは、この配列に1行足すだけで両方に反映される。

### ドライバーの表示形式

**枠と氏名を `X:NAME` の形で1列にまとめる**（例: `A:あそう太郎`）。画面もダウンロードも同じ形式にする。

```js
// 枠（A〜F）と氏名を "A:あそう太郎" の形にする
function formatDriver(slot, name) {
  if (!slot) return "-";        // start_driver 未登録など、枠そのものが無い
  if (!name) return slot;       // 枠はあるが entry に氏名が無い（データ不整合）
  return `${slot}:${name}`;
}
```

| `inDriver` | `inDriverName` | 表示 |
|---|---|---|
| `"A"` | `"あそう太郎"` | **`A:あそう太郎`** |
| `"A"` | `null` | `A` |
| `null` | — | `-` |

レスポンスには枠と氏名が別々に入っているので（§3.2）、表示の形を変えたくなった場合も、この関数を直すだけで済む。

### 列にしない項目

レスポンスの18項目のうち、表に出さないもの。**消すわけではなく、受け取ってはいるので、必要になれば列定義に1行足すだけで出せる。**

| 項目 | 列にしない理由 |
|---|---|
| `inDriver` / `outDriver`（枠単独） | `X:NAME` の形で氏名と合わせて1列にするため |
| `pitNum` | 記録の特定には使うが、表では見ない |
| `pitGarage` | 作業エリアがあれば足りるため |

## 5. ダウンロード

**形式は CSV と PDF の2つ**にする。どちらもサーバーを介さず、画面にあるデータをそのままブラウザ上でファイル化する。

| 形式 | 方法 |
|---|---|
| CSV | 文字列を組み立て、`Blob` にして `<a download>` でダウンロードさせる |
| PDF | `window.print()` を呼ぶ |

> **Excel 形式（SpreadsheetML）から CSV に変更した。** 現行の `outPosts.js` は `.xls` という名前で中身は XML を出しており、Excel のバージョンによっては「形式が拡張子と違う」という警告が出る。CSV なら拡張子と中身が一致するため警告が出ず、組み立ても単純になる。失うのは見出しの太字などの書式だけ。

### 5.1 CSV の作り方（落とし穴あり）

```js
const blob = new Blob([BOM + csv], { type: "text/csv;charset=utf-8" });
const a = document.createElement("a");
a.href = URL.createObjectURL(blob);
a.download = "pit-log-<レースタイトル>-<YYYYMMDD>.csv";
a.click();
URL.revokeObjectURL(a.href);
```

**必ず守ること:**

| # | 内容 |
|---|---|
| 1 | **先頭に BOM（`﻿`）を付ける。** これが無いと、**Excel で開いたときに日本語が文字化けする**。CSV で最も多い事故。メモ帳や Google スプレッドシートでは化けないため、気づきにくい |
| 2 | **エスケープする。** 値に `,` `"` 改行のいずれかが含まれる場合は、その値全体を `"` で囲み、中の `"` は `""` に置き換える。**備考欄（`note`）で実際に起こり得る** |
| 3 | 改行コードは `\r\n` にする（Excel の標準） |

### 5.2 共通の決まり

- **出力する列は、画面に表示している列と同じ**（§4.3 の `PIT_LOG_COLUMNS` を回して作る）。見出しも `label` をそのまま使う。「画面には無いがファイルには入っている」という状態を作らない。
- 出力する内容は、画面で**絞り込み・並べ替えをした後の状態**をそのまま使う（現行の `filterAndSortEntries()` と同じ考え方）。見えているものがそのまま出る。
- ファイル名は `pit-log-<レースタイトル>-<YYYYMMDD>` のように、どのレースのものか分かる名前にする（現行は日付だけ）。

## 6. アクセス記録（`OutpostLog`）

01章の決定どおり、**ダウンロードできる画面では、誰の操作でも残す**。記録のタイミングは**データを取得したとき**（ポップアップを開いたとき）で、ダウンロードボタンを押したときではない。

| 項目                | 内容            |
| ------------------- | --------------- |
| `race_id`           | 対象レース      |
| `username`          | 操作した人      |
| **`is_leader`**     | **その人が leader だったか（真偽値）。新規追加** |
| `id` / `created_at` | ULID / 取得日時 |

記録するかどうかは `act=1` の有無で決まる（§3.3）。確認だけの `showAll.html` は記録しない。

### 6.1 `is_leader` の決め方

**サーバーが判定した値をそのまま記録する。** §3.3 の認可で既に「呼び出し元が leader か」を判断しているので、その結果を使う。クライアントから送らせない（偽装できてしまうため。01章 R2 と同じ考え方）。

### 6.2 「leader かどうか」と「どの画面からか」の違い

この項目が表すのは**人の属性**であり、厳密には「管理者画面から開いたか」ではない。

| 状況 | `is_leader` |
|---|---|
| leader が管理者ポップアップから開いた | `true` |
| **leader が一般の出力画面（outPosts）から開いた** | **`true`** |
| 一般利用者が出力画面から開いた | `false` |

- 管理者ポップアップを開けるのは leader だけなので、**実質的にはほぼ「管理者画面からの取得か」と一致する**。ずれるのは2行目（leader が一般画面を使った場合）だけ。
- 画面そのものを厳密に区別したい場合は、クライアントに「どの画面か」を送らせる必要があるが、その値は偽装できるため、監査記録としては信頼性が落ちる。**サーバーが確実に知っている事実を残すほうを優先する。**

## 7.5 件数の前提（2026-10-09追加）

**Query は1回で最大1MB分しか返さない。** 一般向け・管理者向けのどちらも、当初は
「1レース分は1ページに収まる」前提で `LastEvaluatedKey` を見ていなかった。
`pit_log` 1件が 200〜300バイトなので 1MB は 3000〜5000件に当たり、1レース（数十台 ×
数回のピット = 数百件）なら収まるが、**その前提はどこにも書かれていなかった。**

超えたときに起きることは、黙って一部だけで処理する形になる。

| 影響 | 内容 |
| --- | --- |
| `pit_num` の重複 | `autoCreate` / `handCreate` が「現在の最大 `pit_num`」を数え損ね、回数が巻き戻る |
| 表・CSVの欠落 | `showAll`（`buildPitLogs`）の一覧から記録が落ちる |
| 誤った403 | `getAssignedEntries` が担当エリア内の車両を取り逃がし、その車両の操作が「担当エリア外の車両です」で弾かれる |

**対応（2026-10-09）:** 共通レイヤー `dynamodb.js` に `queryAll(params)` を置き、
最後のページまで辿ってから処理する形に統一した（一般向けの全クエリ11箇所）。
`Limit` は渡さない（`Limit` は「フィルタ前に評価する件数」の上限で、`FilterExpression`
と併用すると取りこぼす。03章§2.5・§4.4 で踏んだ問題と同じ）。
