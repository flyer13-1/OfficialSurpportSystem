# 01 権限モデル（認証・認可）

状態: **確定（2026-09-28）**

管理者画面と管理者APIで「誰が」「何を」できるかを定める。対象は race の管理と、race に属する entry / start_driver / pit_assignment の管理、および終了後の pitlog の参照。

## 1. 用語

| 用語             | 意味                                                                                                                                                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| leader（管理者） | Cognito User Pool の `leader` グループに所属する利用者                                                                                                                                                                                                                    |
| サーキット       | `organizations.circuit`（1〜7）。利用者は `users.organization_id` に1つだけ持つ。race は `race.organization_id` に1つだけ持つ（[SQLcode.sql](../../../database/SQLcode.sql) に準拠）。`6:その他` `7:無所属` も 1〜5 と同格の独立した区分                                  |
| todayId          | `race.today_id`。**当日配布する大会ID**。conform で一度だけ照合される、**パスワードのような値**。予測不可能・全サーキットで一意（02章 §2.3）。口頭・紙などで多くの人に伝えるため、漏れる前提で扱い、漏れたら作り直せる（`raceId` とは別の値にしてある理由）               |
| raceId           | race の識別子（`race.id`）。todayId の照合を通過したクライアントに渡される、**ログイン後のトークンのような値**。以降の一般向けAPIは、これを提示するだけで通る。**有効期限・失効の仕組みが無い**ため、予測不可能性が唯一の防御になる（R9）。全サーキットを通して一意とする |
| 終了済みの race  | `race.finish_date`（DATE、レース終了日）の**翌日 0:00（JST）以降**の race。`finish_date` の当日中は有効                                                                                                                                                                   |
| token            | Cognito が発行した ID トークン。ブラウザでは `sessionStorage["token"]`                                                                                                                                                                                                    |
| sub              | Cognito のユーザー識別子。`users` テーブルの PK（`cognito_sub`）                                                                                                                                                                                                          |

**todayId（パスワード）→ raceId（トークン）の関係:** todayId は一度きりの照合に使い、以降は使わない。raceId は照合を通過した時点で発行され、セッションの間ずっと使われ続ける。raceId には有効期限も失効の仕組みも無いため、予測不可能性だけがその防御になっている（R9）。　**またトークンの機構を作る予定である**

## 2. 基本ルール

| #   | ルール                                                                                                                                                                                                                                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | 管理者APIは「ログイン済み」かつ「leader」かつ「操作対象が自分のサーキットのもの」の3つをすべて満たすときだけ実行する                                                                                                                                                                                |
| R2  | 利用者のサーキットは、必ずサーバーが `users` テーブルから調べる。クライアントが送ってきた値・sessionStorage の値は根拠にしない                                                                                                                                                                      |
| R3  | leader かどうかは Cognito のグループで判定する（`users` テーブルの値は使わない）                                                                                                                                                                                                                    |
| R4  | 他サーキットの race は、一覧に出さず、変更・削除・配下データの登録もできない（6 と 7 も互いに別扱い）                                                                                                                                                                                               |
| R5  | conform での大会ID（todayId）入室は、サーキットで制限しない                                                                                                                                                                                                                                         |
| R6  | leader を外した後も、トークン期限までは管理者扱いが残ることを許容する                                                                                                                                                                                                                               |
| R7  | 終了済みの race には、原則としてアクセスできない。ただし管理者は、自分のサーキットの終了済み race の **pitlog を参照・ダウンロードできる**（§5）                                                                                                                                                    |
| R8  | race の `title` は、同じサーキットの中で重複できない（他サーキットとは重複してよい）                                                                                                                                                                                                                |
| R9  | `raceId` は、todayId の照合を通過した証として機能する**有効期限の無いトークン**である。そのため予測不可能な値にし、全体で重複させない。一般向けAPIはクライアントが送る `race_id` を、この予測不可能性を根拠に信用する（conform で入室した race かどうかを、都度サーバーに確かめる仕組みは持たない） |

## 3. 責務分担

| 層                                                              | やること                                                                                                                                                                                                                     | やらないこと                                                                      |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| フロント: conform                                               | `GET /user/me` の結果から `circuit` を sessionStorage に保存する。`isAdmin` で「管理者画面へ」を表示する。終了済みの race の大会IDを入力したときは、サーバーのメッセージを表示する                                           | —                                                                                 |
| フロント: admin                                                 | `token` と `circuit` の有無だけ検証する。どちらかが無ければ conform.html へ戻す。一覧では終了済みの race を区別して表示し、更新系のボタンを無効にする（見た目だけ）。pitlog はポップアップで表示し、ダウンロードボタンを置く | leader の確認（API の 403 に任せる）。`circuit` や終了の判定を API に送ること     |
| API Gateway ＋ Lambda Authorizer                                | ID トークンの検証（署名・期限・発行元・クライアント・種別）。不正なら拒否。`username` / `sub` / `isAdmin` を後段に渡す                                                                                                       | 権限の判定（通った人には API 全体を許可する）。サーキットや race の期限は知らない |
| 各 Lambda: 管理者向け                                           | `requireAdmin` で leader とサーキットを確認する。対象 race を取得して、サーキットの照合と終了済みの判定をする（§5）                                                                                                          | クライアント指定のサーキットを信用すること                                        |
| 各 Lambda: 一般利用者向け（conform、pitlog の入力・参照・出力） | 対象 race を取得して、終了済みなら拒否する（サーキットでは制限しない）                                                                                                                                                       | —                                                                                 |

sessionStorage は利用者が書き換えられるため、フロントの検証は画面を出し分けるためだけのものであり、安全の根拠は各 Lambda にある。

## 4. `requireAdmin`（共通処理）の仕様

管理者APIのすべての Lambda が、最初に呼ぶ。

1. `authorizer.sub` が無い → **401**
2. `authorizer.isAdmin` が `"true"`（文字列）でない → **403**「管理者権限がありません」。`sub` / `username` / パスをログに残す
3. `users` テーブルを `Key: { cognito_sub: sub }` で取得する。無ければ → **403**「ユーザーが見つかりません」
4. 成功時は `{ username, sub, circuit }` を返す。`circuit` は `users.organization_id`（数値）

## 5. 対象 race の照合と終了済みの扱い

### 5.1 照合の手順（管理者向けAPI）

1. `raceId` から race を取得する。**存在しない、または `race.organization_id` が呼び出し元の `circuit` と一致しない** → どちらも同じ **404**（他サーキットの race の存在を知られないため）
2. 操作が「更新系」で、race が終了済みなら → **403**「終了したレースです」（`reason: "race_finished"`、§6）
3. 「参照系（pitlog の参照・ダウンロード）」なら、終了済みでも実行する

race に属するデータ（entry / start_driver / pit_assignment / pitlog）は、必ず先にこの手順で race を照合する。

- **一覧:** 自分のサーキットの race を、終了済みも含めて返す。終了済みかどうかが分かる情報を付ける。
- **登録:** `organization_id` はサーバーが呼び出し元の値を付ける。リクエスト body の値は受け付けない（無視する）。

### 5.2 操作ごとの可否

| 操作                                                     | 一般利用者                  | 管理者（自分のサーキット）  |
| -------------------------------------------------------- | --------------------------- | --------------------------- |
| conform での大会ID入室                                   | 終了済みなら不可（**403**） | —                           |
| pitlog の入力（自動・手入力・リタイア・更新）            | 終了済みなら不可（**403**） | —                           |
| pitlog の参照・出力（一般向け画面）                      | 終了済みなら不可（**403**） | —                           |
| **pitlog の参照・ダウンロード（管理者画面）**            | —                           | **終了後も可**              |
| race の一覧                                              | —                           | 可（終了済みも表示）        |
| race の変更・削除                                        | —                           | 終了済みなら不可（**403**） |
| entry / start_driver / pit_assignment の登録・変更・削除 | —                           | 終了済みなら不可（**403**） |

管理者の pitlog 参照・ダウンロードは、一般向けの `showAll`（`GET /entries/show`）のデータ生成の仕組みを流用する。ただし認可は管理者向け（`requireAdmin` ＋ §5.1 の照合）で行い、画面は admin.html の中のポップアップ（新規）にダウンロードボタンを置く。

古い race の整理（削除・並べ替えなど）は、今は扱わない。使われ方を見て、将来の機能として検討する。

### 5.3 終了判定

- 判定は各 Lambda がサーバー側で行う。Lambda は UTC で動くため、**JST に直した日付**と `finish_date` を比べる（今日 > `finish_date` なら終了済み）。
- クライアントの時刻や sessionStorage は使わない。

### 5.4 照合の手順（一般向けAPI）

conform、pitlog の入力・参照・出力のAPIが対象。サーキットでは制限しない。

1. `race_id` から race を取得する。存在しなければ **404**「対象のレースが存在しません」
2. race が終了済みなら **403**「終了したレースです」（`reason: "race_finished"`）

## 6. ステータスコード

| コード          | 意味                                                      |
| --------------- | --------------------------------------------------------- |
| 401             | 未ログイン（`sub` が取れない）                            |
| 403             | 次の3つ。`msg` で区別し、判別用に `reason` も返す（下表） |
| 404             | 対象が存在しない、または他サーキットのもの                |
| 400 / 409 / 500 | 各APIの章で定める                                         |

| 403 の理由           | `reason`         | `msg`                        |
| -------------------- | ---------------- | ---------------------------- |
| leader でない        | `not_admin`      | 「管理者権限がありません」   |
| `users` に登録が無い | `user_not_found` | 「ユーザーが見つかりません」 |
| 終了済みの race      | `race_finished`  | 「終了したレースです」       |

## 7. 画面の挙動

| 場面                                                          | 動き                                         |
| ------------------------------------------------------------- | -------------------------------------------- |
| admin を開いたとき `token` または `circuit` が無い            | conform.html へ戻す（履歴を残さない）        |
| トークンが不正・期限切れ（API が 401、または `fetch` が例外） | 認証情報を消して、強制的にログイン画面へ戻す |
| API が 403 で `reason` が `not_admin` または `user_not_found` | `msg` を表示し、conform.html へ戻す          |
| API が 403 で `reason` が `race_finished`                     | `msg` を表示するだけ（画面は移動しない）     |

- 不正なトークンは、API Gateway が Authorizer の拒否として返すレスポンスになる。このレスポンスには CORS ヘッダーが付かないと思われ、その場合ブラウザでは `fetch` が例外になる。401 で返る場合と例外になる場合のどちらでも同じ処理（ログインへ戻す）にするため、レスポンスの形に依存しない。
- 通信が切れて `fetch` が例外になった場合も、同じ扱いでログイン画面へ戻る。これは許容する。

### 決定済み（参考）

- 終了の境界は「`finish_date` の翌日 0:00（JST）以降」。
- 古い race の整理（削除・ソート）は、今は考えず、将来の機能として検討する。
- 403 の理由の判別には `reason` を使う（採用）。conform の IF（[userMenu1.md](../../userMenu1.md)）にも反映済み。
- 一般向けAPIの `race_id` は、`raceId` を予測不可能・全体一意にすることで守る。conform で入室した race かどうかをサーバーに記録する仕組みは設けない（R9）。
- 一般向けAPIで race が存在しないときは 404。
- ダウンロードの形式は Excel と PDF（既存の出力画面と同じ）。
- ダウンロードの記録は、一般利用者も管理者も、誰の操作でも残す（`OutpostLog` に `username` / `race_id` / 日時）。記録するのは、既存の出力画面と同じく、データを取得したとき。

## 9. 将来の拡張候補（今回は見送り）

- **署名付きトークンによる race アクセス制御。** 今の設計（R9）は、`raceId` の予測不可能性**だけ**で一般向けAPIの安全性を保っている。より堅牢にするなら、conform 通過時にサーバーが `{ raceId, exp }` を署名したトークンを発行し、各 Lambda がその署名を検証してから `race_id` を信用する方式（`authorizer.mjs` が Cognito トークンを検証するのと同じ考え方）にする。この方式なら `raceId` 自体は予測可能でもよくなり、`finish_date` を `exp` に埋め込めば終了判定もトークン検証だけで完結する。
- **見送った理由。** 対象ファイルが backend 約10本（pitlog 系7本＋entry 系3本）・frontend 約7本に及び、署名鍵の管理・共通検証処理の新設・全画面の動作確認まで含めると、実装からテストまで10〜14時間規模の見積もりになった。残りの製作期間（約半月）を踏まえ、今回のコストには見合わないと判断した。
- **前提。** admin 関連のファイルはこの後の章でいずれ見直され、作り直される予定のため、後からこの方式に切り替えても大きな手戻りにはならない。R9（`raceId` を暗号論的乱数にする）は、その置き換えまでの間の実装として維持する。**このトークン機構は、作る方針で確定している**（§1 参照）。
