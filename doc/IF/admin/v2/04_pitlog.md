# 04 pitlog の参照・ダウンロード（管理者画面・一般画面 共通）

状態: **ドラフト（レビュー待ち）**

ピット記録（`pit_log`）を画面に出し、ダウンロードするための設計。**管理者画面のポップアップと、一般向け画面（`showAll.html` / `outPosts.html`）を同じ仕組みに統一する。**

本章で定めるのは次の3つ。

1. **バックエンドのデータ処理**（§2）
2. **送信形式**（§3）
3. **フロントでの表示方法**（§4）

ダウンロード（§5）以降は、管理者画面向けの話として残す。権限の共通ルールは [01_permission.md](01_permission.md) に従う。

## 1. 位置づけ

3つの画面は、**同じデータ・同じ形式・同じ描画処理**を使う。違うのは次の3点だけ。

| 画面                    | 見られる race                                  | 出力（ダウンロード） | ログに残すか |
| ----------------------- | ---------------------------------------------- | -------------------- | ------------ |
| `showAll.html`（確認）  | 入室中の1レースのみ（終了すると見られない）    | できない             | **残さない** |
| `outPosts.html`（出力） | 入室中の1レースのみ（終了すると見られない）    | できる               | 残す         |
| 管理者ポップアップ      | **所属サーキットの全レース**（終了済みも含む） | できる               | 残す         |

- **見られる race の違いは、画面が持っている `raceId` の数で決まる。** 一般画面は conform で入室したときの `raceId` を sessionStorage に1つ持つだけなので、そのレースしか見られない。管理者ポップアップは一覧から選ぶため、自分のサーキットのレースならどれでも開ける。
- **終了済みを見られるかは、画面ではなく人（leader かどうか）で決まる。** 01章 §5.1 と §5.4 の違いがそのまま出る。そのため、leader が一般画面を開いた場合は、終了済みのレースでも 403 にならない（見られるのは入室中の1レースのみという点は変わらない）。
- `raceId` はヘッダー（`X-Race-Id`）で送る（01章 R10）。

## 2. バックエンドのデータ処理

### 2.1 現状の問題（`showAll.mjs`）

今は1本の Lambda が、データ取得・加工・認可・記録を全部やっている。直すべき点は3つ。

| #   | 現状                                                                                          | 直す内容                   |
| --- | --------------------------------------------------------------------------------------------- | -------------------------- |
| 1   | 認可が `username` の有無だけ。race の存在確認も終了判定もサーキット照合も無い                 | §3.3 の認可を通す          |
| 2   | レスポンスが ULID をキーにしたオブジェクト。フロントは結局 `Object.keys()` で配列に戻している | 最初から配列で返す（§3.1） |
| 3   | 仮キーを書いてすぐ消す無意味なコードが残っている（`result[...] = null` → あとで `delete`）    | 削除する                   |

### 2.2 共通化: `buildPitLogs(raceId)`

データを組み立てる部分を、Layer（`/opt/nodejs/`）の共通関数に切り出す。認可も記録も**含めない**（呼び出し側の責任にする）。

やること（現行 `showAll.mjs` の処理をそのまま移す）:

1. `pit_log` / `entry` / `retire` / `start_driver` を `race_id` で並列に Query する
2. 車番 → ピット回数の昇順に並べる
3. `inDriver` を算出する（`pitNum=1` は `start_driver` の値、2以降は**同じ車の前回ピットの `outDriver`**）
4. `pitGap` を算出する（`garageInTime` が null かつ `inTime` / `outTime` が揃っているときだけ、秒数で）
5. `entry` から `className` / `teamName`、`retire` から `retire` を引いて合成する
6. **配列**で返す

## 3. 送信形式

### 3.1 レスポンス（3画面共通）

```json
{
  "msg": "",
  "logs": [
    {
      "manager": "あそう太郎",
      "pitNum": 1,
      "carNum": 5,
      "className": "ST-1",
      "teamName": "チームA",
      "retire": false,
      "inDriver": "A",
      "outDriver": "B",
      "inTime": "2026-08-30T13:05:00+09:00",
      "outTime": "2026-08-30T13:07:30+09:00",
      "garageInTime": null,
      "pitGap": 150,
      "tire": true,
      "oil": false,
      "note": ""
    }
  ]
}
```

- 0件のときは `logs: []`。
- 並び順は車番 → ピット回数の昇順（画面側で並べ替え直せる）。同時刻のときは `pitNum` → `carNum` の順で決める（結果が毎回同じになるように）。

**`pit_log.id`（ULID）は返さない。** 理由は次のとおり。

- 記録の書き換え（`PUT /entries/update`）は `race_id` + `carNum` + `pitNum` で対象を特定しており、ULID を使っていない（[updatePut.mjs](../../../../backend-sam/functions/pitlog/updatePut.mjs) で確認済み）。
- 表示にも出力にも使っていない。現行の `showAllGimic.js` は同時刻の並べ替えに使っているが、ULID は文字列のため `a.managerId - b.managerId` が `NaN` になり、**実際には何もしていない**。
- 使わない内部キーを画面や通信に流さないほうが安全（`raceId` と同じ考え方。01章 §1）。

### 3.2 項目

| 項目                                  | 内容                                                    |
| ------------------------------------- | ------------------------------------------------------- |
| `manager`                             | 記録した担当者                                          |
| `pitNum` / `carNum`                   | **ピット回数**（何回目のピットインか。場所ではない。§8）/ 車番 |
| `className` / `teamName`              | `entry` から引く                                        |
| `retire`                              | `retire` テーブルから引く                               |
| `inDriver`                            | `pitNum=1` は `start_driver`、2以降は前回の `outDriver` |
| `outDriver`                           | 出たときの運転者                                        |
| `inTime` / `outTime` / `garageInTime` | 時刻（ISO 8601）                                        |
| `pitGap`                              | ピット滞在秒数。算出できないときは `null`               |
| `tire` / `oil` / `note`               | 作業内容・備考                                          |

### 3.3 エンドポイントと認可

**エンドポイントは1本にする。** 3画面とも同じものを呼び、Lambda が呼び出し元の権限を見て扱いを変える。

`GET /entries/show`（既存のパスを流用）

| クエリ  | 内容                                                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------- |
| `act=1` | 付けると `OutpostLog` に記録する（§6）。`outPosts.html` と管理者ポップアップが付ける。`showAll.html` は付けない |

処理の順序:

1. `authorizer.sub` が無ければ **401**
2. `raceId`（ヘッダー）から race を取得する。無ければ **404**
3. **呼び出し元が leader か**で分岐する
   - **leader の場合:** `race.organization_id` が自分のサーキットと違えば **404**。終了済みでも続行する（01章 §5.1）
   - **leader でない場合:** サーキットは見ない。終了済みなら **403**（`reason: "race_finished"`、01章 §5.4）
4. `buildPitLogs(raceId)` でデータを組み立てる
5. `act=1` なら `OutpostLog` に記録する
6. 返す

> **なぜ1本にするか:** 返すデータも形式も同じで、違うのは認可だけ。2本に分けると、ほぼ同じ中身の Lambda を2つ保守することになる。「終了済みを見られるかは、どの画面から呼んだかではなく、その人が leader かどうかで決まる」という考え方に揃える。

### 3.4 エラー

| 条件                           | コード | msg                                                 |
| ------------------------------ | ------ | --------------------------------------------------- |
| 未ログイン                     | 401    | 「認証が必要です」                                  |
| race が存在しない              | 404    | 「対象のレースが存在しません」                      |
| leader で、他サーキットの race | 404    | 同上（存在を知られないため）                        |
| leader でなく、race が終了済み | 403    | 「終了したレースです」（`reason: "race_finished"`） |
| サーバーエラー                 | 500    | 「サーバーエラーが発生しました」                    |

## 4. フロントでの表示方法

### 4.1 現状の問題（`showAllGimic.js` をそのまま流用できない理由）

描画処理は `showAllGimic.js` にあるが、今の作りのままでは管理者ポップアップで使えない。

| #   | 現状                                                                      | 起きること                                                                                                                   |
| --- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 1   | 読み込み時に `getElementById("all")` / `("search")` / `("filter")` を取る | admin.html にこれらのIDが無いと `null` になり、末尾の `allButton.addEventListener(...)` で例外が出て**スクリプト全体が死ぬ** |
| 2   | `document.querySelector("tbody")` で描画先を決めている                    | admin.html には既に別の表（レース一覧・プレビュー）があるため、**最初に見つかった別の表に描いてしまう**                      |
| 3   | グローバル変数 `entries` を直接読む                                       | `admin.js` と変数名が衝突する                                                                                                |
| 4   | 列数が `colSpan = 12` で固定                                              | 列構成を変えると崩れる                                                                                                       |

### 4.2 共通化の方針

`showAllGimic.js` から **DOM の決め打ちとグローバル変数を取り除き、引数で受け取る純粋な関数にする。**

| 関数                                                | 役割                                       |
| --------------------------------------------------- | ------------------------------------------ |
| `filterAndSortPitLogs(logs, { className, search })` | 絞り込みと並べ替えをして、新しい配列を返す |
| `renderPitLogTable(tbody, logs)`                    | 渡された `tbody` に行を描く                |
| `formatDatetime` / `formatGap` / `formatBoolean`    | 表示用の整形（現行のまま）                 |

- **イベントの紐付け（検索欄・クラスボタン・全表示ボタン）は、各画面の側に移す。** `showAll.js` / `outPosts.js` / `admin.js` が、自分の画面にある要素を自分で拾って、上の関数を呼ぶ。
- これにより、`showAllGimic.js` は「どの画面から呼ばれても同じように動く部品」になる。
- 管理者ポップアップでも、一般画面と同じ絞り込み・並べ替えがそのまま使える。

## 5. ダウンロード

`outPosts.js` の実装を流用する。

| 形式  | 方法                                                                           |
| ----- | ------------------------------------------------------------------------------ |
| Excel | SpreadsheetML（`.xls`）をクライアント側で組み立て、`Blob` でダウンロードさせる |
| PDF   | `window.print()` を呼ぶ                                                        |

- ファイル名は `pit-log-<レースタイトル>-<YYYYMMDD>.xls` のように、どのレースのものか分かる名前にする（現行は日付だけ）。
- **列の範囲は要確認。** 現行の `outPosts.js` は12列だけ出しており、`garageInTime` / `tire` / `oil` を落としている。管理者向けは記録保全が目的のため、全項目を出す案（§8 未決事項）。

## 6. アクセス記録（`OutpostLog`）

01章の決定どおり、**ダウンロードできる画面では、誰の操作でも残す**。記録のタイミングは**データを取得したとき**（ポップアップを開いたとき）で、ダウンロードボタンを押したときではない。

| 項目                | 内容            |
| ------------------- | --------------- |
| `race_id`           | 対象レース      |
| `username`          | 操作した人      |
| `id` / `created_at` | ULID / 取得日時 |

記録するかどうかは `act=1` の有無で決まる（§3.3）。確認だけの `showAll.html` は記録しない。

## 8. 未決事項

- **ダウンロードの列。** 全項目（16項目）にするか、現行の出力画面と同じ12列に合わせるか。
- **`OutpostLog` に管理者かどうかの区別を足すか。** 今は `username` だけで、管理者画面からの取得か出力画面からの取得かを区別できない。
- **PDF の出力方法。** `window.print()` のままでよいか（ポップアップの中身だけを印刷するには CSS の調整が必要）。
- **エンドポイント名。** `GET /entries/show` を流用する前提で書いたが、中身はピット記録なので `GET /pit-log` に改名する案もある（改名すると `template.yaml` とフロント2本の修正が増える）。
- **`pitNum` の改名（2026-10-01 議論、結論持ち越し）。** 「pit」が付く項目が3つあり、意味が逆の印象を与えて混乱しやすい。
  | 今の名前 | 意味 | 持ち主 |
  |---|---|---|
  | `pit_num` | 何回目のピットインか（**回数**） | pit_log |
  | `pit_garage` | ピットガレージ番号（**場所**。`T1` 等の文字列） | entry |
  | `maintenance_area` | Pit前作業エリア（**場所**。数値） | entry |

  実装を確認した結果、`pit_num` は**回数で確定**している（`autoCreate.mjs` / `handCreate.mjs` が `max+1` で採番し、`showAll.mjs` は `pit_num === 1` をスタートドライバーの判定に使う）。改名するなら `pit_num` → `pit_count` が候補だが、DB列・API・フロント（`when`）・ソート処理と7ファイル以上に及ぶ。**残り工数を踏まえ、まずは設計書に意味を明記するだけに留める案を推奨**。改名の可否は未決。
