# raceId トークン設計書

状態: **確定（2026-10-03）**。未決事項（§10）を全て解消済み。実装の着手時期は別途判断（§8参照）。

一般利用者向けAPIが `race_id` を信用する根拠を、「値が推測しにくいこと」から「**サーバーの署名があること**」に変えるための設計。

- 対象は **一般利用者向けAPI**（conform / pitlog の入力・参照・出力 / 一般向け start_driver 登録）。**管理者向けAPIは対象外**（§9）——`requireAdmin` とサーキット照合で既に安全性を担保しており、`raceId` の秘匿性に頼っていないため。
- 権限の共通ルールは [admin/v2/01_permission.md](../aws-sam/admin/v2/01_permission.md) に従う。本書は、そこで「将来の拡張候補」としていた仕組み（§9）を具体化したもの。

## 1. 今の方式と、その弱点

現在（01章 R9）は、`raceId` を暗号論的乱数にして、**「知っている＝正規に入室した」とみなしている**。

| # | 弱点 |
|---|---|
| 1 | **失効できない。** `raceId` が一度漏れると、そのレースに永久にアクセスできる |
| 2 | **conform を通らなくても使える。** 他人の `raceId` を何らかの方法で入手すれば、大会ID（`todayId`）を知らなくても使える |
| 3 | **`raceId` に制約がかかる。** 推測されては困るため、連番など分かりやすい値にできない |
| 4 | 終了判定のたびに race をDBから引く必要がある |

## 2. 変えること

| | 今 | トークン方式 |
|---|---|---|
| クライアントが送るもの | `raceId` そのもの | **署名付きの文字列** |
| 信用する根拠 | 推測しにくい値を知っていること | **サーバーの鍵で署名されていること** |
| `raceId` に必要な性質 | 予測不可能 | **不問**（連番でも可） |
| 有効期限 | 無い | **あり**（トークンに埋め込む） |
| 第三者への譲渡 | できてしまう | **できない**（§3 の `sub` で縛る） |

> すでにこのシステムで動いている `authorizer.mjs`（Cognito のトークンを検証する仕組み）と同じ考え方。違いは、Cognito が鍵のペアを使うのに対し、こちらは**発行と検証が同じサーバー**なので同一の鍵で済む（HMAC）点だけ。

## 3. トークンの構造

```
eyJyYWNlSWQiOiJrUTN2Li4uIn0.7f2a9c4e8b1d...
└────── 中身（Base64URL） ──────┘ └── 署名 ──┘
```

**中身（ペイロード）**

| 項目 | 例 | 意味 |
|---|---|---|
| `raceId` | `"kQ3v9Zp2mT8xLw1nYb7RcA"` | どのレースに対する証明か |
| `sub` | `"8f41c2a0-..."` | **誰に発行したか**（Cognito の利用者識別子） |
| `exp` | `1788000000` | いつまで有効か（UNIX秒） |

**署名**: 上の中身を、サーバーだけが持つ秘密鍵で HMAC-SHA256 したもの。

> **中身は暗号化しない。** Base64 は誰でも元に戻せるので、`raceId` は読めてしまう。この方式が守るのは「**中身を読まれないこと**」ではなく「**中身を書き換えられないこと**」。書き換えれば署名と合わなくなり、検証で弾かれる。

### `sub` を入れる理由

利用者を縛ることで、**トークンを他人に渡しても使えなくなる**。検証時に、トークンの `sub` と、Cognito トークンから得た `sub`（`authorizer.sub`）が一致するかを確認する。

- 同じレースに入る人は、それぞれが自分で conform を通すため、各自が自分のトークンを持つ。運用上の支障はない。
- 別の端末でログインし直した場合も、conform をやり直して新しいトークンを受け取る。

## 4. 発行（conform）

`POST /user/me` で `todayId` が一致したときに、サーバーが作ってレスポンスに載せる。

```
① 中身を組み立てる        → {"raceId":"kQ3v...","sub":"8f41...","exp":1788000000}
② JSON文字列にして Base64URL 変換
③ ②を秘密鍵で HMAC-SHA256 → 署名
④ ②と③を「.」でつないで返す
```

レスポンス（[userMenu1.md](userMenu1.md) の更新が必要）:

```json
{
  "msg": "",
  "raceToken": "eyJyYWNlSWQiOi...7f2a9c4e..."
}
```

- **`raceId` は返さなくなる。** クライアントが `raceId` を直接扱う必要がなくなるため。
- 終了済みのレースは、そもそもここで 403 になるので、トークンは発行されない。

## 5. 検証（各API）

共通処理を1つ作り、`race_id` を使う**一般向けAPI**が最初に呼ぶ（`requireAdmin` と同じ置き場所・同じ使い方。ただし呼ぶのは一般向けAPIだけで、管理者向けAPIは呼ばない。§9参照）。

```
① X-Race-Id ヘッダーの文字列を「.」で分ける → 中身 と 署名
② 中身を自分の秘密鍵で HMAC 計算し、受け取った署名と比べる
   └─ 一致しない → 401（偽造・改ざん）
③ 中身の sub と authorizer.sub を比べる
   └─ 一致しない → 401（他人のトークン）
④ 中身の exp と現在時刻を比べる
   └─ 過ぎている → 401（期限切れ）
⑤ すべて通れば、中身の raceId を信用して処理を進める
```

- **署名の比較は、タイミング攻撃を避けるため `crypto.timingSafeEqual` を使う。** 単純な `===` だと、一致する文字数の差で処理時間が変わり、総当たりの手がかりを与える。
- 検証に失敗した理由（偽造・他人・期限切れ）は、**レスポンスでは区別しない**（攻撃者に手がかりを与えないため）。ログには残す。

### 既存の照合との関係

管理者向けAPIはこの設計の対象外であり、今まで通り `requireAdmin` ＋ サーキット照合（01章§5.1）＋生の `raceId` による race 取得のまま変わらない。

一般向けAPIは、トークン検証の後にやることも01章§5.4のまま変わらない。

| 操作 | トークン検証の後にやること |
|---|---|
| 一般向けAPI | race の存在確認（§5.4）。**終了判定は `exp` で済むため、DBアクセスを1回減らせる**（§7） |

## 6. 秘密鍵の管理

| 項目 | 方針 |
|---|---|
| 置き場所 | **SSM Parameter Store（SecureString）** に置き、Lambda から読む。`template.yaml` に平文で書かない |
| 長さ | 32バイト以上の乱数（`crypto.randomBytes(32)`） |
| 読み込み | コールドスタート時に1回だけ読み、以降は使い回す |
| 権限 | 各 Lambda のロールに、そのパラメータの読み取り権限を追加する |

> 既存の `template.yaml` は `COGNITO_USER_POOL_ID` などを環境変数に平文で書いているが、**これらは秘密ではない**（公開されても害がない識別子）。署名鍵は本物の秘密なので、同じ扱いにしてはいけない。

### 作成・設定の手順（マネジメントコンソール）

鍵は「人が決める」値ではなく、**ローカルで乱数を1回生成してコピペするだけ**。コードや `template.yaml` には一切書かない。

1. **鍵の生成（ローカル端末）**

   どちらかのコマンドで、32バイトの乱数をBase64文字列にする。

   ```bash
   # Node.js（プロジェクトの実行環境と揃える）
   node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

   # もしくは OpenSSL
   openssl rand -base64 32
   ```

   出力された文字列をコピーする。この値はどこにも保存せず、次の手順でSSMに貼ったら手元の控えは残さない（ターミナルの履歴にも残るため、作業後はクリアすることが望ましい）。

2. **SSM Parameter Store にパラメータを作成する**

   AWSマネジメントコンソール → **Systems Manager** → 左メニュー「パラメータストア」→「パラメータの作成」

   | 項目 | 設定値 |
   |---|---|
   | 名前 | `/OfficialSupportSystem/${Env}/race-token-secret`（`Env` は `dev`/`stg`/`prod`。環境ごとに別パラメータにし、鍵を使い回さない） |
   | 階層 | 標準（無料枠で足りる） |
   | タイプ | **SecureString** |
   | KMSキー | 既定の `alias/aws/ssm` でよい（専用CMKにする理由がなければそのまま） |
   | 値 | 手順1でコピーした文字列を貼り付け |

   「パラメータの作成」で完了。

3. **Lambda に読み取り権限を追加する（コード側）**

   発行・検証を行う各Lambdaのロールに、このパラメータだけを対象にした `ssm:GetParameter` を許可する（`Resource: "*"` にしない）。`template.yaml` のポリシー追加が必要。

4. **Lambda 側の読み込み**

   環境変数には**パラメータの名前だけ**を置く（例 `RACE_TOKEN_SECRET_PARAM`）。値そのものは環境変数にもコードにも書かない。`layers/common/` の共通処理が、コールドスタート時に `GetParameterCommand`（`WithDecryption: true`）で1回だけ取得し、モジュールスコープの変数にキャッシュして使い回す。

### 鍵を変えると何が起きるか

**発行済みの全トークンが無効になり、全員が conform からやり直しになる。**

- レース中に行うと現場が混乱するため、**レースとレースの間に行う**。
- 逆に言えば、「全員を強制的に締め出す」手段としても使える（漏洩が疑われるときの最終手段）。

## 7. 有効期限（`exp`）の決め方

**そのレースの `finish_date` の翌日 0:00（JST）** とする。01章の「終了済み」の定義（§1）と同じ。

| 利点 | 内容 |
|---|---|
| 自然に失効する | レースが終われば、トークンも使えなくなる |
| DBアクセスが減る | 一般向けAPIの終了判定が、署名検証だけで済む |

**例外: `finish_date` が無い場合（2026-10-07追加）**

`finish_date` は02章§2でレース登録時の必須項目のため本来起こらないが、データの欠損や
改ざんで消えた場合に**期限の無いトークンを出さない**ための安全策を置く。

| 項目       | 扱い                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| `exp`      | **現在時刻 + 2時間**（`conform.mjs` の `MISSING_FINISH_DATE_EXP_SECONDS`） |
| 超過後     | `exp` 切れとして一般向けAPIが403（`reason: race_finished`）を返す          |
| 画面への通知 | レスポンスに `warning: "finish_date_missing"` を付け、管理者への連絡を促す（[userMenu1.md](userMenu1.md#終了日が無いレースについて2026-10-07追加)） |

終了済みの判定そのものは `finish_date` が無いとできないため行わない。つまり
**入室は許すが2時間で失効する**という形になる。

**注意: `finish_date` を後から変更した場合**（02章 §4 で変更可能）

| 変更の向き | 起きること | 対応 |
|---|---|---|
| **短縮**（終了日を早める） | 発行済みトークンは古い（長い）期限のまま残る | ずれを許容する。厳密に締め出したい場合は鍵の変更が必要 |
| **延長**（終了日を遅らせる） | 発行済みトークンが先に期限切れになる | **利用者は conform をやり直す**（大会IDを再入力）。運用で周知する |

## 8. 実装の進め方

**プレリリース前（本番の利用者が一人もいない）ため、段階移行は行わず一括で最終形に実装する。** 旧方式（生の `raceId` を信用する）との互換コードは最初から書かない。

| # | 内容 |
|---|---|
| 1 | 秘密鍵を SSM に作成する（§6） |
| 2 | 共通処理（発行・検証）を `layers/common/` に実装する |
| 3 | `conform.mjs` を、トークンだけを返す形に実装する（生の `raceId` は返さない） |
| 4 | pitlog系7本・entry系の一般向けLambda（`init` / `POST /entries/start-driver`）を、トークン検証に置き換える（生の `raceId` の受付コードは作らない）。**管理者向けAPI（race系・admin系）は対象外**（§9参照） |
| 5 | フロント全画面をトークン送信に合わせて実装する（§9） |
| 6 | 一括でデプロイし、全画面を通しで動作確認する |

> 本番でレースが稼働している状態でこの設計を導入する場合は、入室済み利用者への影響を避けるため段階移行に戻すこと。上記はあくまで「プレリリース前」という前提での簡略化。

### 決定済み（参考）

- **秘密鍵の置き場所（2026-10-03）:** SSM Parameter Store（SecureString）に確定。環境変数案は採らない（平文で残るため）。作成・設定の手順は§6に記載済み。
- **`raceId` の生成方法（2026-10-03）:** 生成はサーバー側のまま変えないが、**専用の暗号論的乱数生成（16バイト→Base64URL22文字）は廃止し、`generateId()`（`layers/common/nodejs/dynamodb.js`。pit_log / pit_log_history / outpost_log と同じULID生成関数）を流用する**。
  - 今の `generateId()` は内部で `Math.random()` を使っており、02章§2.3の「暗号論的な乱数（`crypto`）。`Math.random` は使わない」という要件を満たさない。しかしトークン方式では `raceId` の安全性が「値の予測不可能性」ではなく「署名が正しいこと」で担保される（§2）ため、これは問題にならない。`raceId` はDBキーとして一意であればよく、ULIDの衝突耐性で十分。
  - 専用の生成コードを持たずに済むため実装・保守コストも下がる。`todayId` は今も秘密そのものなので対象外（暗号論的乱数のまま、変更なし）。
  - プレリリース前で既存データが無いため、既存データとの整合は論点にならない。実装時に**02章§2.3の表を更新する**（`raceId` 行を「ULID（`generateId()`）」に変更）。
- **着手の時期（2026-10-03）:** プレリリース前で本番利用者がいないため、段階移行（旧§8）は行わず**一括で最終形に実装する**（§8）。
